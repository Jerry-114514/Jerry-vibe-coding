# 《大模型方案.md》核查意见与执行调整

日期：2026-10-16。来源为用户提供的 `D:/Download/大模型方案.md`；原文件保持不变。以下区分可采用的架构、需要修正的事实和仍需预检的假设。

## 可采用的架构

采用“服务端教师推理/生成缓存，现有 AutoDL 4090 训练学生”的分工，能避免 32B/72B 教师权重占用本机显存和磁盘。审计推理只需要文本，不必取得 logits；训练可另设使用教师文本的序列蒸馏配置。

这解决的是教师部署问题，不自动证明 7B 学生的所有输入预算都能在 24GB 中训练。精确开源检查点阶梯、商业 API 外部验证和不同蒸馏损失分别标注。

## 必须修正的内容

| 原文件主张 | 核查结论与执行规则 |
|---|---|
| `qwen-vl-plus/max` 分别代表“32B/72B 级” | 未取得参数量及检查点映射的官方证据，不能这样标注，也不能放进精确 Qwen2.5-VL 参数阶梯。商业端点单列。 |
| DashScope 没有精确参数命名模型 | 官方部署与计费文档列有 `qwen2.5-vl-32b-instruct`、`qwen2.5-vl-72b-instruct`、7B 等标识；但目录存在不等于当前账号已开通直接推理。优先验证精确模型、部署方式和版本，不用别名替代。[官方部署计费说明](https://help.aliyun.com/zh/model-studio/model-training-and-deployment-billing)、[按 Token 部署](https://help.aliyun.com/zh/model-studio/model-deployment-token) |
| `-latest` 用于冻结版本 | 它是可变别名，不是不可变快照。使用实际存在且可调用的日期版本/部署 ID，并记录请求返回模型标识；`2026XXXX` 是占位符。官方公告说明 latest 会指向新快照。[官方更新公告](https://help.aliyun.com/zh/model-studio/application-release-notes) |
| 全部 DashScope 视觉模型不支持 logprobs | 支持情况依型号变化。当前兼容接口说明部分模型（包括 qwen3-vl-plus）支持，`top_logprobs` 上限为 5；这仍不能替代原 top-50、token ID 对齐、tail-bucket KL。[官方参数说明](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions) |
| 用同一个 plus 接口桥接本地 3B/7B | 不是同一检查点的后端桥接。只有能准确定位同一 3B/7B 检查点及对应预处理时，才有这种解释。否则是不同模型的性能比较；分差小也不能证明权重/量化相同。 |
| 原损失是 `0.5 CE_label + 0.5 KL` | 当前真实实现的 CE 使用缓存中的 **教师回答 token**，不是训练真值标签。原式是 `0.5 CE_teacher_response + 0.5 KL_top50_tail`。新增 `CE_label` 必须单独注册，不能当成不变协议。[现有代码](../tools/train_distill.py) |
| SeqKD 一定仅比 KL 差 1–3% | 不能作本实验的效果保证。引用的 arXiv:2404.14827 讨论机器翻译中的情境差异，不能直接推出视觉任务的固定差距。[论文原文](https://arxiv.org/abs/2404.14827) |
| 7B 训练约 17–20GB，可直接认定可行 | 是待测估计。当前全 BF16 的 7B 推理分配峰值约 16.006 GiB；反向激活、LoRA 梯度和优化器另计。主训练前必须做实际更新预检。 |
| 增加 `gate_proj/up_proj/down_proj` 没有额外协议影响 | 会增加可训练参数，也可能匹配 Qwen 视觉 MLP；必须按完整模块路径限制为语言层，先保留原 q/k/v/o，再将 MLP LoRA 作为独立消融。否则显存和训练处理因素同时变化。 |
| batch=1 时增大梯度累积可自动解决 OOM | 不会减少单个样本的激活峰值。优先使用梯度检查点和训练时 `use_cache=False`；确需调整图像/文本预算时，只在开发预检阶段调整，冻结后所有臂一致。 |
| 14B BF16 可与 7B 一样直接放进 24GB | 按标称 14B 每参数 2 字节，纯权重已约 26.1 GiB，不含视觉/激活开销。API、显式 CPU offload 或量化才可能绕过全 GPU 驻留；量化单列敏感性。[官方模型卡](https://huggingface.co/OpenGVLab/InternVL3-14B) |
| 可直接采用文件中的成本和耗时 | 当前模型、区域、部署方式、图像 token 和账号价格均需验证；先抽样测真实 usage，再核算全部审计、教师、学生评测与 GPU 费用，不能承诺文件中的总预算。 |

## 当前已经取得的实测证据

以下均为旧数据上的开发/工程预检，不是新增独立确认结果。

| 项目 | 真实完成规模 | PyTorch 分配峰值 | 判定 |
|---|---:|---:|---|
| Qwen 3B 全 BF16 推理 | 800 条，四轴各 100 原题单元 | 7.573 GiB | 完成；原始输出、严格解析和精度差异已保存 |
| Qwen 7B 全 BF16 推理 | 同上 | 16.006 GiB | 完成；未超过 24GB |
| Qwen 3B BF16 LoRA+KL 工程预检 | 100 次实际更新，四轴各 25 次 | 7.755 GiB | 独立核验通过；有限损失、非零 LoRA B、adapter 与恢复状态一致 |
| Qwen 7B BF16 教师文本 CE 工程预检 | 100 次实际更新，四轴各 25 次 | 16.275 GiB；reserved 18.852 GiB | 独立核验通过；旧 7B 教师文本，未调用付费 API |
| 原数据 CPU 补分析 | 三家族、120 设置×4 臂、共同样本域、1,000 次图像簇重采样 | 不分配 CUDA | 完成；保持为探索性分析 |

3B 训练保留固定的旧 7B 教师缓存，隔离学生 BF16 可行性；它不是“新增 API 教师已接通”。单个短程预检不能代表完整多种子训练的统计结论。

CPU 补分析确认：Qwen 原经验商集的 `F=0.08333` 对应一个全平局类、严格反转比例为零；A1−A2 的原始增益和 floor 增益配对区间均跨零。新正式预算 gate 仍未开放。

InternVL 2B/8B 的 BF16 各 800 条预检也已完成，allocated 峰值分别为 4.880/15.787 GiB。LLaVA 0.5B 的进程切换空闲检查失败已修复并恢复运行。统一使用 GPU 锁、23GiB PyTorch 预算和完成后自动 GitHub 备份。阶段状态以各自 `complete.json` 和验收记录为准。

## 后续执行调整

1. 继续当前不超过 24GB 的预检；7B 的序列 CE 训练已补做 100 步实测，保留原 q/k/v/o LoRA 和 `use_cache=False`，不直接增加视觉/MLP LoRA。该预检通过不代表任意长输入、多图或其他 LoRA 结构都不会 OOM。
2. API 客户端分成“精确开源检查点审计”和“商业教师序列蒸馏”两种身份；显式配置 endpoint、模型/版本、图像预算、返回 usage、失败重试和缓存键。
3. 主线先保留原 KL 桥接；新增 teacher-text CE 与真实标签 CE 分开定义，并增加固定教师条件的机制对照，不同时更换教师与损失后声称只测到了教师参数效应。
4. 校准、审计和确认继续按来源图像隔离；只能在校准集上调整 API 提示与坐标契约，不允许看审计/确认结果后反复“调到一致”。
5. 暂不把四节点直接加入旧 OWA。先用三节点；四节点必须另行定义三条边权重并注册。
6. API 密钥、模型访问和费用上限落实后，才提交有费用的批量任务。本机 `DASHSCOPE_API_KEY`、`SILICONFLOW_API_KEY`、`OPENROUTER_API_KEY` 环境变量目前均未配置；文件中的 `sk-xxx` 只是示例。
